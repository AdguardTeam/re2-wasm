## Project Overview

`@adguard/re2-wasm` is a fork of Google's [re2-wasm](https://github.com/google/re2-wasm)
that adds a configurable maximum memory limit for regular expressions. It
compiles Google's [RE2](https://github.com/google/re2) C++ library to WASM
via Emscripten and exposes it as a drop-in replacement for JavaScript's
`RegExp`. The library is a critical dependency of the AdGuard Browser
Extension, where it validates user-supplied regular expressions for the
Declarative Net Request API with predictable, linear-time matching and
bounded memory usage.

## Build And Test Commands

```bash
# Install dependencies (does not compile — only Node deps)
npm install

# Full build: compile C++ → WASM via Emscripten, compile TypeScript, write build info
npm run compile

# C++ → WASM compilation only (via Docker Emscripten image)
npm run compile-emcc

# TypeScript compilation only
npm run compile-ts

# Run tests (compiles first via pretest, then lints via posttest)
npm test

# Lint TypeScript sources
npm run lint

# Auto-fix lint issues
npm run fix

# Clean build artifacts
npm run clean

# Bump patch version (no git tag)
npm run increment
```

The full build pipeline is:

1. **C++ → WASM**: `make -j12` invokes Emscripten to compile `wrap/re2_wrap.cc`
   and all RE2 source files into `wasm/re2.js`
2. **TypeScript → JS**: `tsc` compiles `src/re2.ts` into `build/src/`
3. **WASM assets**: `wasm/` directory is copied into `build/`
4. **Build info**: `scripts/build-info.js` writes `build/build.txt`

## Code Guidelines

### System Design

Design for a library:

- The library is consumed by other code — never access the filesystem, network,
  or environment unless the caller explicitly opts in. Keep side effects out of
  the default code path.
- Export a stable public API; internal functions and types MUST be explicitly
  marked as private or internal.
- Keep the dependency footprint minimal — every transitive dependency becomes a
  burden on consumers. Prefer built-in APIs over adding packages.
- Do not mutate global state (environment variables, process listeners, shared
  singletons) — the consumer may use the library in a long-running process
  alongside other code.
- Provide complete type definitions so the library is usable with static type
  checking and editor autocompletion out of the box.
- Document every public function, class, and type with doc comments — consumers
  should not need to read source code to use the library.
- Handle errors by throwing specific, documented error classes — let the
  consumer decide how to recover.

### Architecture

Universal design principles:

- **Separation of Concerns** — each layer handles one aspect of regex execution:
  JS API, WASM bridge, C++ engine.
- **Single Responsibility Principle** — `RE2` class implements the `RegExp`
  interface; `WrappedRE2` handles C++ → WASM translation; `translateRegExp`
  converts syntax.
- **Dependency Direction** — dependencies point downward: JS → WASM → C++.
  Never the reverse.
- **Explicit Boundaries** — the WASM interface is defined in `wasm/re2.d.ts`
  and generated by Emscripten bindings in `wrap/re2_wrap.cc`. No direct calls
  across boundaries.
- **Data Flow Clarity** — pattern string flows from `RE2` constructor through
  `translateRegExp` → `WrappedRE2` → Google RE2. Match results flow back up
  the same chain.
- **Minimize Coupling, Maximize Cohesion** — the `RE2` class is self-contained;
  the only external dependency is the WASM module.
- **Make Invalid States Impossible** — the `u` flag is enforced in the
  constructor; invalid patterns throw `SyntaxError` immediately.
- **Observability Built-in** — less critical for this library; error reporting
  is handled through standard `SyntaxError` and descriptive error messages from
  RE2.
- **Keep It Boring** — uses well-established technologies: Emscripten, Google
  RE2, plain TypeScript. No experimental or novel approaches.

The project uses a **layered architecture**:

1. **JavaScript API** — Implements the `RegExp` interface (`exec`, `test`, `match`,
   `replace`, `search`, `split`); translates JS regex syntax to RE2 syntax.
   Examples: `src/re2.ts` (`RE2` class, `translateRegExp`).
2. **WASM Bridge** — Type declarations for the compiled WASM module;
   auto-generated Emscripten JS glue.
   Examples: `wasm/re2.d.ts`, `wasm/re2.js`.
3. **C++ Bindings** — Emscripten bindings wrapping Google RE2 C++ objects with
   WASM-compatible interfaces (no out-parameters).
   Examples: `wrap/re2_wrap.cc` (`WrappedRE2` class).
4. **RE2 Library** — Google's RE2 regex engine — linear-time,
   non-backtracking regular expression matching.
   Examples: `deps/re2/` (vendored submodule).

Dependency flow:

```text
JavaScript API (src/re2.ts)
     ↓
WASM Bridge (wasm/re2.js, wasm/re2.d.ts)
     ↓
C++ Bindings (wrap/re2_wrap.cc)
     ↓
RE2 Library (deps/re2/)
```

Each layer may only depend on the layer directly below it. No layer may depend
on a layer above it.

### Code Quality

- **Documentation**: Public methods on the `RE2` class are documented with
  JSDoc comments. Internal helpers (`translateRegExp`, `escapeRegExp`,
  `isHexadecimal`) have explanatory comments referencing their origins.
- **Linting**: The project uses `gts` (Google TypeScript Style), which bundles
  ESLint and Prettier. Configuration is inherited from `gts` in `.eslintrc.json`
  and `.prettierrc.js`. Do not modify these config files without discussion.
- **Type checking**: TypeScript strict mode is enabled via `gts`. All code in
  `src/` is type-checked. The `RE2` class aims to match the `RegExp` interface
  but cannot formally `implement RegExp` due to a TypeScript limitation
  (microsoft/TypeScript#42307 — documented in the source).
- **Error handling**: Errors are thrown immediately for invalid input (pattern
  syntax errors, missing `u` flag, duplicate group names). The `compile()`
  method throws an explicit deprecation error.
- **Naming conventions**: PascalCase for classes (`RE2`, `WrappedRE2`),
  camelCase for functions and variables (`translateRegExp`, `escapeRegExp`),
  `I`-prefix for interfaces (`InternalMatchResult`), `_`-prefix for private
  class fields (`_global`, `_ignoreCase`).
- **Imports**: ES module imports (`import { WrappedRE2 } from '../wasm/re2'`).
  Test files use CommonJS `require`.

### Testing

- **Framework**: heya-unit (`third_party/node-re2/tests/tests.js` is the test
  runner).
- **Test file placement**: All tests live in `third_party/node-re2/tests/`,
  adapted from the [node-re2](https://github.com/uhop/node-re2) test suite.
- **Test naming**: Files follow `test_<feature>.js` convention (e.g.,
  `test_exec.js`, `test_match.js`, `test_invalid.js`).
- **Test organization**: Each test file registers test functions with
  `unit.add(module, [ function test_*(t) { ... } ])`. Assertions use
  `eval(t.TEST("expression"))`.
- **Verification**: Tests MUST pass before merge. The full test suite is run
  via `npm test`, which compiles first then runs tests then lints.
- **Coverage**: No coverage tooling is currently configured.
- **The `test_invalid.js`** test verifies that memory limits, backreferences,
  and lookahead assertions are properly rejected.

### Dependency Management

- **Pin all dependency versions explicitly** — use exact versions, not ranges.
  The lock file (`package-lock.json`) is committed and enforces deterministic
  installs.
- **Prefer vanilla solutions** — this library has only build-time dev
  dependencies. The runtime has zero npm dependencies; all functionality comes
  from the compiled WASM module.
- **Reputable sources only** — dependencies are limited to `gts` (Google),
  `typescript` (Microsoft), and `heya-unit` (testing). All are well-established
  packages.
- **Avoid unpopular libraries** — do NOT add niche or obscure packages with
  limited community adoption. These pose security risks and may become
  unmaintained.
- **Minimize dependency count** — each new dependency increases attack surface
  and maintenance burden. Justify every addition.
- **Use the latest stable version** — when adding a new dependency, check the
  npm registry for the latest stable release and use it. Do not copy outdated
  version numbers from training data or existing lock files.

**Known exclusions** (to be fixed):

- `package.json` uses caret ranges for all devDependencies (`^14.11.2`,
  `^3.1.0`, `^0.3.0`) and a tilde range for TypeScript (`~4.1.3`). These
  should be pinned to exact versions.

- **Configuration**: There is no runtime configuration. Build configuration is
  in `Makefile` (Emscripten flags), `tsconfig.json` (TypeScript options), and
  `package.json` (npm metadata).
- **Secrets**: No secrets or API keys are used in this project.
- **Documentation files to update when code changes**:

### Markdown Formatting

All Markdown files MUST follow these formatting rules:

- **Line length**: Keep lines at most 120 characters, but don't overwrap the
  lines artificially short just to hit the limit, keep them close to 120
  characters where possible. This is not a hard lint gate, but SHOULD be
  followed for readability. Lines inside fenced code blocks are exempt from
  this limit.
- **Unordered lists**: Use dashes (`-`) for bullet points. Indent nested list
  items by 4 spaces.
- **Continuation lines**: When a list item wraps to the next line, align the
  continuation with the first character of the item text, not the list marker.
  This applies to all list types (ordered and unordered).
- **Emphasis**: Use asterisks (`*`) for emphasis (`*italic*`, `**bold**`). Do
  NOT use underscores.
- **Headings**: Duplicate heading names are allowed only among sibling headings
  (same parent level). Avoid duplicates across different levels.
- **Inline HTML**: Avoid raw HTML in Markdown. The only allowed element is
  `<a>`.
- **Trailing spaces**: Do NOT leave trailing whitespace on any line. Do NOT use
  two-space line breaks — use a blank line instead.
- **Bare URLs**: Bare URLs are permitted and do not need to be wrapped in angle
  brackets.
- **Table formatting**: Align table columns with padding when the table fits
  within 120 characters. If the table exceeds 120 characters or triggers an MD060
  linter warning, switch to a compact format using single spaces only. This
  applies to the separator row as well — it should be written as `| --- |`,
  not `|--|`.

  Example of correct layout:

  ```markdown
  | Col1 | Col2 |
  | --- | --- |
  | Value1 | Value2 |
  ```

  Do NOT use extra padding or alignment characters beyond single spaces.

**Rationale**: Uniform Markdown formatting improves readability for both humans
and AI agents that consume project documentation.
